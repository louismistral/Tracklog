# Tracklog — répertoire du projet

Application web (PWA) de suivi personnel : trackers configurables + suivi
nutritionnel, données synchronisées sur Supabase. Un seul utilisateur par
compte, pensé pour PC et téléphone (installable en PWA).

Ce document est la carte du projet : le vocabulaire (pour que le nom d'un
concept soit toujours le même dans le code, les commits et la conversation),
la liste des écrans, l'inventaire des fonctionnalités, l'architecture
technique, et les pièges connus. Un seul fichier, tenu à jour à la main —
pas de source de vérité parallèle.

## Fichiers

| Fichier | Rôle |
|---|---|
| `Tracklog.html` | Page unique. CSS complet inline (thème « Aristide »), balises `<script>` qui chargent React/Supabase/Babel depuis un CDN puis `app.jsx` et `app.food.jsx` en JSX brut (transformé dans le navigateur par Babel standalone — pas de build). |
| `app.jsx` | Cœur : modèle de données trackers/entries, auth, tous les écrans sauf Food. ~4200 lignes. |
| `app.food.jsx` | Page Food : bibliothèque d'aliments, scanner de code-barres, journal de repas, objectifs. Second `<script type="text/babel">`, chargé après `app.jsx` — partage son scope global (React, `supabase`, `dayKey`, `uid`…). ~3000 lignes. |
| `index.html` | Redirige vers `Tracklog.html`. |
| `foods-ref.json` | Table Ciqual 2025 (ANSES) compactée en colonnes — 3341 aliments crus/cuits avec micronutriments, servie en statique pour la recherche hors-ligne d'aliments sans étiquette. |
| `manifest.json`, `icon-*.png`, `apple-touch-icon.png` | PWA — installable sur téléphone. |
| `tools/ciqual/` | Source Excel d'origine de la table Ciqual (génère `foods-ref.json`). |
| `supabase/functions/analyse-repas/` | **Le seul morceau de serveur.** Edge Function Deno qui appelle Claude pour décomposer un repas décrit en texte. Existe pour que la clé API Anthropic reste côté serveur — contrairement à la clé anon Supabase, elle n'a aucune protection propre. Déployée sur le projet, `verify_jwt` actif ; il lui faut le secret `ANTHROPIC_API_KEY` pour répondre autre chose qu'une erreur de configuration. |

Pas de bundler, pas de `package.json`, pas de tests automatisés. Les CDN
(unpkg React/Babel, jsdelivr) sont épinglés par version + intégrité SRI dans
`Tracklog.html`.

## Lexique

| Terme | Définition |
|---|---|
| **Tracker** | Une chose qu'on suit dans le temps (ex. Caféine, Humeur, Sport). A un `type`, un nom, une couleur, une fréquence. Se remplit avec des **Entries**. |
| **Entry** (entrée) | Une valeur enregistrée pour un tracker à un instant `ts`. `{ id, trackerId, value, note, ts }`. |
| **Type** de tracker | `number` (nombre + unité) · `scale` (échelle 1–N) · `boolean` (oui/non) · `duration` (minutes) · `choice` (options prédéfinies, simple ou multiple) · `text` (note libre) · `master` (calculé, voir ci-dessous). |
| **Master** | Un tracker `type:'master'` qui ne se remplit jamais lui-même : sa valeur du jour est la **moyenne normalisée (0–100)** de ses trackers **membres**. Sert d'indice composite (« Forme », « Discipline »…). |
| **Membre** | Un tracker de données rattaché à un master (`master.members: string[]`). |
| **Quotidien** (`daily`) | Un tracker qui n'accepte qu'une entrée par jour ; ré-enregistrer remplace la valeur du jour. |
| **Plusieurs/jour** | `daily: false` — autant d'entrées que voulu par jour, combinées via l'**agrégat**. |
| **Agrégat** (`aggregate`) | Comment combiner plusieurs entrées du même jour pour un tracker `number`/`duration` non quotidien : `avg` (moyenne, défaut) · `sum` · `min` · `max`. |
| **Échelle personnalisée** (`scaleMin`/`scaleMax`/`scaleStep`) | Un tracker `scale` définit son propre intervalle et son propre incrément (ex. -100 à 100 par pas de 1), pas juste un « 1 à N » — la valeur par défaut reste 1–5 par pas de 1 pour les trackers déjà créés. |
| **Sens de l'amélioration** (`goodDirection`/`targetValue`) | Pour un tracker `number`/`scale`/`duration` : `up` (monter = mieux, défaut) · `down` (descendre = mieux, ex. temps d'écran) · `target` (se rapprocher de `targetValue` = mieux, peu importe de quel côté). Décide, dans les vues composites (Master, Tendance générale, Grille), de quel côté est le progrès — sans ça, un tracker « moins c'est mieux » ferait chuter la moyenne composite quand il s'améliore. |
| **Joker** | Un marqueur posé sur une journée entière (`value: '__joker__'`) qui **exclut** ce jour de tous les calculs — pas un zéro, une journée hors calcul (repos, écart planifié…). Option par tracker (`jokerEnabled`), sans effet sur un tracker quotidien. |
| **Fenêtre d'activité** (`windowEnabled`, `startDate`/`endDate`) | Bornes de dates hors desquelles un tracker n'influence ni les graphes ni les moyennes. `startDate` par défaut = date de création ; `endDate` posé automatiquement à l'archivage. |
| **Graphe cumulatif** (`cumulative`) | Option d'affichage (nombre/durée uniquement) : le graphe trace la somme cumulée depuis le début plutôt que la valeur du jour — courbe qui ne peut que monter. |
| **Forme de courbe** (`curveStyle`) | `line` (polyligne, défaut) · `smooth` (courbe lissée, Catmull-Rom passant exactement par chaque point) · `bars` (un bâton par point, rien entre eux). Purement visuel. |
| **Cartes par ligne** (`perRow`) | Le curseur « − / + » de la vue Cartes : de 1 à 4 cartes de graphe par ligne. Ce n'est pas qu'une largeur — chaque cran retire du détail (statistiques, graduations) et rapetisse le graphe, jusqu'à la sparkline. Remplace l'ancien couple d'affichages Liste / Grille, qui n'étaient que deux crans de ce même réglage. |
| **Granularité** (`chartGrain`) | `day` (défaut) · `week` (lundi→dimanche) · `month` — ce qu'un point du graphe couvre. Les jours d'une même période sont ramenés à leur **moyenne** (un tracker cumulatif prend la valeur de fin de période). Réglage indépendant de la forme de courbe. |
| **Archiver** | Masque un tracker du "Jour" et le range dans Paramètres → Archives, sans supprimer ses entrées. Réversible (désarchiver, depuis le même `TrackerModal`). |
| **Chrono** | Un chronomètre, synchronisé compte (table `chronos` + Supabase Realtime) : démarré sur un appareil, il apparaît démarré sur les autres — seul l'horodatage de départ voyage, le décompte affiché reste calculé localement. Réordonnable comme les cartes du Log. Peut se lier à un tracker `duration` : « Enregistrer » convertit le temps écoulé en entrée. |
| **Mode Solo/Multi** (chronos) | Solo = démarrer un chrono met les autres en pause automatiquement ; Multi = ils tournent en parallèle. |
| **Master Strip** | Bande compacte (jauge 0–100) affichant la valeur du jour d'un master, en haut du "Jour" et de l'"Historique". |
| **Rail** (filtre) | Le panneau de pastilles cliquables (un tracker = une pastille) qui filtre les vues par sélection de trackers. Trois boutons séparés au-dessus — **Filtres**, **Tri** (Manuel/A→Z/Récents/Type), **Grouper** — chacun son panneau, chacun son état ouvert/fermé : trois questions différentes qui ne tiennent plus dans un seul intitulé. Tout survit au rechargement, par appareil (`tracklog.filter.<userId>`), comme les chronos. |
| **Grouper** | Le troisième bouton du rail : décide comment le "Jour" range ses trackers en **sections** — `type` (Quotidiens / Plusieurs par jour / Alimentation / Masters, le cas d'origine), `couleur` (une section par couleur de tracker utilisée, identifiée par sa seule pastille), `fait` (Fait aujourd'hui / Pas fait — un joker compte comme fait). Le tri décide l'ordre *dans* une section ; grouper décide *en combien* de sections et lesquelles. |
| **Section** (du Jour) | Un bloc du "Jour" — Masters, Quotidiens, Plusieurs par jour, Alimentation, ou une section couleur/fait selon le groupement — réordonnable au même titre qu'une carte de tracker (poignée `DragHandle`, même geste d'appui maintenu). Un ordre par mode de groupement (`sectionOrders`), recalé sur les sections réellement présentes à chaque rendu (`mergeSectionOrder`). |
| **Appui maintenu** | Au doigt, un glisser (réordonner) et la lecture d'un graphe ne s'arment qu'après ~350 ms / ~260 ms d'appui immobile. Tant que l'attente court, rien n'est bloqué : partir avant la fin fait simplement défiler la page. À la souris tout reste immédiat — il n'y a pas de défilement à confondre avec l'intention. |
| **Aliment** | Une fiche nutritionnelle "pour 100 g/ml", et l'un des deux types d'**item**. Son `source` dit son **origine** (voir plus bas) : `'ref'` · `'off'` · `'ai'` · `'custom'`. |
| **Food log** (ligne de repas) | Une portion mangée à un jour/repas donné. Garde un **snapshot** figé des valeurs nutritionnelles au moment de la saisie — corriger la fiche d'un aliment plus tard ne réécrit pas l'historique déjà loggé. |
| **Repas** | Une des 4 catégories fixes du jour : `matin` (petit-déjeuner) · `midi` · `soir` · `collation`. |
| **Macro** | Les 4 compteurs "de tête" de la page Food : kcal, protéines, glucides, lipides — seuls à avoir un objectif et un graphe. |
| **Objectifs** (`nutrition_goals`) | Cibles quotidiennes kcal/protéines/glucides/lipides ; valeurs par défaut tant que rien n'est réglé. Kcal se règle toujours en dur ; chaque macro a son propre **mode** (`{macro}Mode`) — `grams` (un chiffre posé) · `percent` (% des kcal cible, converti via 4 kcal/g protéines/glucides, 9 lipides) · `perkg` (g par kg de **poids** — `weightKg`, propre au compte). La source de vérité est le mode + son **ratio** (`{macro}Ratio` : le %, ou le g/kg) ; les grammes qu'il produit sont ce que tout le reste de l'app lit, recalculés à l'enregistrement — pas un lien live qui suivrait un changement de poids fait ailleurs. |
| **Consigne datée** (`fromDay`) | Un objectif n'est pas un réglage global mais une consigne **à partir d'un jour**. La clé de `nutrition_goals` est `(user_id, from_day)` ; le jour J lit la dernière consigne dont `from_day <= J` (`goalsAt`, `effectiveGoalsAt`, `goalsSetAt`). Changer d'objectif vaut donc pour ce jour-là et les suivants — les jours d'avant gardent le leur, et un graphe sur 90 jours dit la vérité sur toute sa longueur. La date de prise d'effet est celle du **jour qu'on regardait** en ouvrant la fenêtre. |
| **Portions** (`meals.portions`) | Ce qu'une recette **produit** (« ce plat fait 4 parts »). À ne pas confondre avec ce qu'on en **prend**, demandé à chaque ajout (`MealPortionModal`, une demie comprise). Les ingrédients pèsent toujours la recette entière : une portion est une division, pas une saisie de plus à tenir à jour. |
| **Item** | Tout ce qu'on peut verser dans une journée et qui reste à soi : un aliment (`foods`) ou un repas enregistré (`meals`). Une ligne de journal n'en est pas un — c'est la trace d'un item mangé. |
| **Origine** (`source`) | D'où vient un item, en quatre valeurs et pas une de plus : `ref` (**aliment simple** — table Ciqual, officiel, sans code-barres) · `off` (**aliment à code** — Open Food Facts, produit emballé) · `ai` (**item IA** — sorti d'une analyse) · `custom` (**personnel** — créé à la main). Registre unique dans `ITEM_ORIGINS` (app.food.jsx), lu par `itemOrigin()`. Colonne persistée sur `foods` **et** sur `meals`. |
| **Pastille d'origine** (`OriginTag`) | L'étiquette colorée que porte tout item, partout où il se montre — ligne de résultat, carte de bibliothèque, carte de repas. Un contour, pas un aplat : c'est une provenance, pas un état. |
| **Sous-catégorie** (`itemSub`) | Le second niveau, qui existait déjà et n'est pas refait : groupe Ciqual pour un aliment simple, marque pour un produit à code, « analyse » pour un item IA. Un aliment simple qui rejoint la bibliothèque perd son groupe (pas de colonne pour ça) mais garde son code `ciqual:…` — `itemSub` le retrouve via `refByBarcode`. |
| **Favori** (`favorite`) | Un item mis de côté, retrouvable d'un geste. La même étoile pour un aliment et pour un repas : ce sont deux items, elle ne peut pas vouloir dire deux choses. |
| **Engrenage** (`GearIcon`) | L'icône unique de « ouvrir les réglages de cette chose » — cartes du Log, cartes de graphe, calendrier, tuiles de la Grille, master strips, objectifs de Food. Un seul composant : les SVG recopiés à la main avaient dérivé vers un cercle à rayons qui se lisait comme un soleil. |
| **Ingrédient** | La monnaie commune entre l'analyse IA et les repas : `{ id, name, grams, per100, foodId?, note? }`. Les valeurs sont **pour 100 g**, le poids est à part — corriger un poids recalcule les macros sans rien redemander. Ce n'est **pas** un item : c'est un composant d'un repas, qui ne vit que dans sa liste (le champ `foodId` le relie à un item quand il en vient d'un). |
| **Repas enregistré** (`meals`) | Un **preset** : une liste d'ingrédients qu'on ajoute d'un coup, plus une recette facultative. C'est un item : il porte une origine (`custom` ou `ai`) et un favori. Ne pas confondre avec le **Repas** au sens catégorie du jour ci-dessus. |
| **Étape** (`steps`) | Une ligne de recette : `{ id, text, done, mins }` — `mins` est le minuteur facultatif. L'`id` existe pour le glisser-déposer (on déplace une ligne, pas un rang) ; `done` est la case cochée. Le **numéro n'est jamais stocké** — il se lit de l'ordre affiché, donc réordonner renumérote tout seul. Les repas d'avant portaient de simples chaînes : `stepsFromRows` les relit sans rien perdre. |
| **Analyse IA** | Décrire un repas en texte, en photo, ou les deux, et récupérer sa décomposition en ingrédients pesés. Passe par l'Edge Function `analyse-repas`, jamais par le navigateur directement. Ce qui en sort **peut** devenir un item (`source:'ai'`) — la page le demande, elle ne le décide pas. |
| **Mode d'analyse** (`mode`) | `normal` — le modèle estime de tête, vite. `advanced` (« Approfondi ») — il a la recherche web (la carte du restaurant qu'on nomme, la fiche d'un produit) **et** remplit les micronutriments. Un seul champ dans la requête ; côté fonction il change le système, le schéma (les micros ne sont demandés qu'en approfondi) et l'outil `web_search`. Les URL réellement consultées reviennent dans `sources` et sont affichées. |
| **Écriture optimiste** | Toute écriture de la page Food pose l'état local d'abord et envoie derrière : la page se referme sans attendre le réseau. En échec, elle **défait** ce qu'elle a affiché et le dit (`writeFailed`) — c'est la contrepartie obligatoire, un échec muet étant pire que l'attente. |
| **Créer** | Le quatrième onglet de l'ajout, où l'on pose les chiffres soi-même, en trois sous-modes qui ne fabriquent pas la même chose : *Ajout rapide* (kcal + macros versées dans la journée, **pas un item** — un correctif de journée) · *Aliment* (les mêmes, plus le poids mangé, ce que les macros décrivent, et — facultatif — son code-barres : un item à soi) · *Repas* (ouvre l'éditeur de repas). Chaque sous-mode empile ses questions dans des cartes (`.card.fd-card`) plutôt qu'un long formulaire à filets. Le code-barres n'est plus un mode à part : c'était le même formulaire avec un champ de plus. |
| **Barre à icône** (`IconBar`) | L'autre forme de contrôle partagée, à côté de `Segmented` : une barre pleine largeur et **un** bouton rond. Deux formes, et la différence est un sens, pas une décoration. `inset` — le bouton est **dans** la barre, sous le même contour, parce qu'il ne fait que la remplir autrement (la recherche et son scanner). `detached` — le bouton est **à côté** : la barre montre quelque chose, le bouton agit dessus (la bascule Aliments/Repas et l'étoile qui la filtre). Le rond reste un `.icon-btn`. |
| **Style** (`STYLES`, `data-theme`) | Un jeu de variables CSS sous `:root[data-theme="<id>"]`. En ajouter un = un bloc de tokens dans `Tracklog.html`, une entrée dans `STYLES` (app.jsx) et son id dans `STYLE_IDS` (script en tête de page). Préférence **par appareil**. |
| **Préférences de compte** (`user_settings`) | Un blob `jsonb` par compte, et la référence pour tout réglage : `prefs.tabs` (onglets affichés), `prefs.tabOrder` (leur ordre), `prefs.theme`, `prefs.help`, `prefs.showWeek`, `prefs.cameraOn`. Tracklog se vit sur téléphone **et** sur PC : un réglage posé d'un côté doit se retrouver de l'autre. `localStorage` n'en garde qu'un miroir (voir `useSyncedPref`). Renommer un onglet ne renomme pas sa clé déjà enregistrée : l'ancien id `bouffe` est relu au chargement et reporté sur `food` (voir « Renommer un onglet » dans les pièges). |
| **Réglage synchronisé** (`useSyncedPref`) | Un réglage qui suit le compte avec un miroir `localStorage` : le miroir s'affiche tant que la base n'a pas répondu (le style est même lu par un script en tête de page, avant l'app), puis le compte gagne et corrige l'appareil. |
| **Retour** (`feedback`) | Un message envoyé depuis les paramètres : `kind` (bug · feature · avis · autre), le texte, et un `context` capté automatiquement (style, taille d'écran, navigateur). |

## Écrans

Navigation par onglets en haut (`tab`), certains avec sous-onglets (`Sub`).

| Onglet | Sous-onglet | Composant | Description |
|---|---|---|---|
| **Log** | Jour | `TodayView` → `DayGrid`/`DayCard` | Remplir aujourd'hui : une carte éditable par tracker actif, regroupées Quotidiens / Plusieurs par jour. Bouton « + Nouveau tracker » en tête. Bouton "Tout ajouter" groupé. Affiche les Master Strips et le résumé Food du jour. |
| | Historique | `HistoryView` → `MonthCalendar` + `DayGrid` | Calendrier mensuel (points = jours avec entrées) ; cliquer un jour ouvre son éditeur en dessous (identique au "Jour" mais sur une date passée). Reçoit aussi les sauts directs depuis le tooltip d'un graphe (`jumpTo`). |
| | Chrono | `ChronoView` → `ChronoCard` | Chronomètres, liés ou non à un tracker durée. Fenêtre flottante (Picture-in-Picture navigateur) pour garder les chronos visibles pendant qu'on fait autre chose. |
| **Food** | Jour | `FoodDayView` | Repas du jour par catégorie, barres de progression vers les objectifs, panneau détail/micronutriments dépliable, navigation jour précédent/suivant. |
| | Aliments | `FoodLibraryView` | Trois vues sur ce qui est à soi : Mes aliments · Mes favoris · Mes repas. Recherche, étoile favori, lien vers la fiche source, création/édition de repas. |
| | Vues | `FoodVuesView` → `NutritionBars` | Graphe en barres d'une macro sur N jours vs objectif, + répartition calorique P/G/L. |
| **Vues** | Graphes / Calendrier / Grille | `VuesView` → `ChartCard`/`MasterChart`/`TrendChart`/`CalendarCard`/`GridSummary` | Visualisation multi-tracker sur une période choisie (7/30/90/365j, YTD, tout, personnalisé) : courbes individuelles, overlay Master normalisé, tendance moyenne lissée, heatmap calendrier, grille de KPI. Dans Graphes, la barre « Affichage » choisit entre **Cartes** (une carte par tracker, densité au curseur), **Master** et **Tendance**. |
| **Training** | — | `TrainingView` | Réservé — le suivi d'entraînement viendra ici. Masquable tant qu'il est vide. |
| **AI analyst** | — | `AnalystView` | Réservé — Claude y lira les trackers ensemble (corrélations, régularités, ce qu'un master doit à un seul membre). L'onglet existe, le contenu viendra. |
| **Paramètres** | — | `SettingsView` | Compte · Style · Onglets (`TabsSettingsCard` : afficher/masquer **et** réordonner) · Affichage (explications, numéro de semaine) · **Archives** (trackers archivés, seul point d'accès pour les désarchiver) · Un retour ? (`FeedbackCard`). Chaque réglage porte sa description écrite en dessous (`Help`). |
| *(hors onglets)* | — | `SignIn` | Connexion / création de compte / lien magique / mot de passe oublié. |

Pas d'onglet « Trackers » séparé : chaque carte du Log et chaque Master Strip
porte son propre engrenage vers `TrackerModal`, et « + Nouveau tracker » est en
tête du Log — le rail de filtre garde aussi son propre bouton d'ajout. Un
tracker archivé n'a plus de carte nulle part pour porter un engrenage ; la
liste **Archives** des paramètres est donc son seul chemin de retour.

`MealEditModal` est, comme la page d'ajout et malgré son nom, une **page
entière** (`.fd-add-page`) — trois cadres : le titre, les ingrédients, la
recette. « ＋ Ajouter un ingrédient » y rouvre `AddFoodModal` en **mode
choisir** : une recette se compose donc d'un produit scanné, d'un aliment
Ciqual, d'une analyse IA ou d'un autre repas entier, par les mêmes quatre
onglets que l'ajout d'une journée — aucun de ces chemins n'est réécrit pour
l'occasion.

`TrackerModal` (créer/éditer un tracker ou master) est, malgré son nom et
comme `AddFoodModal`/`MealEditModal`, une **page entière** (`.fd-add-page`) —
quatre cadres en cartes (Cœur, Paramètres, Vues, Couleur) plutôt qu'une boîte
étroite au-dessus du Log : les champs à choix (genre, fréquence, courbe,
granularité) y sont des pastilles pleine largeur (`Segmented size="compact"`),
pas des chips à leur contour.

Modales transverses restantes : `EntryModal` (éditer une entrée existante),
`ChronoModal`, `AddFoodModal`, `FoodEditModal`, `MealEditModal`, `GoalsModal`,
`PasswordModal`.

`AddFoodModal` est **la page d'ajout** : le bouton principal de Food n'ouvre
plus un scanner mais elle, et le scan n'y est plus qu'une façon d'arriver parmi
quatre. Malgré son nom (gardé pour ne pas casser tous les appels), ce n'est
plus une modale mais une page plein écran (`.fd-add-page`) — quatre onglets ont
besoin de place pour respirer, pas d'un couloir centré avec sa propre limite de
hauteur. Titre et onglets (`.fd-add-head`, `.fd-add-tabs`) restent fixes en
haut, seul `.fd-add-body` défile. Une seule rangée de quatre onglets, qui sont
quatre gestes distincts :

| Onglet | Ce qu'on y fait | Composant |
|---|---|---|
| Recherche | Chercher dehors — Ciqual, Open Food Facts — dans **une** barre à icône `inset` qui accepte aussi bien un nom qu'un code-barres ; son bouton rond sort la caméra sous elle. Les trois provenances tombent dans **une seule liste**, triée : nom exact d'abord, puis favoris, puis déjà enregistré. | recherche OFF/Ciqual + `FoodScanner` |
| Mes items | Reprendre ce qui est déjà à soi : la même barre de recherche qu'à côté, puis une barre à icône `detached` qui porte la bascule Aliments/Repas, l'étoile (favoris) et le bouton vignettes. | liste filtrée · `MealsTab` |
| IA | Décrire, photographier, ou les deux. Deux rectangles pleine largeur : la photo (un « + » au centre), puis le texte, puis la bascule Normal / Approfondi. | `AiAnalyseTab` |
| Créer | Poser les chiffres soi-même : un correctif de journée, un aliment à soi, ou un repas entier (voir **Créer** au lexique). | `QuickAddTab` |

Les sept onglets d'avant, répartis sur deux rangées, mélangeaient « où je
cherche » et « quoi je cherche » — le scan était un onglet à lui seul alors que
c'est une façon de remplir la recherche, et « à la main » ne disait pas ce
qu'il fabriquait. Rien n'a disparu : ils sont devenus les sous-bascules de ces
quatre.

## Fonctionnalités

- **Trackers configurables** — 6 types de données + un type calculé (master), fréquence quotidienne ou multi-entrées, agrégat, unité, couleur, fenêtre d'activité, archivage réversible. Chaque carte du Log porte son propre engrenage vers les réglages (`TrackerModal`) — pas d'onglet dédié, voir « Écrans ».
- **Case joker** — exclure une journée entière des calculs sans la compter comme un échec. Sur la carte, active un bouton rond (icône « annuler ») et remplace la ligne de saisie par un tiret « — · ce jour ne compte pas » plutôt que de laisser un champ vide inviter à noter quelque chose.
- **Masters (indices composites)** — moyenne normalisée 0–100 de plusieurs trackers, avec bande de lecture (Master Strip) et carte graphe dédiée.
- **Graphes par tracker** avec axes auto-arrondis (`niceDomain`/`niceStep`), pontage en pointillés des trous de données, mode cumulatif optionnel.
- **Échelle verticale intelligente** — les bornes sont l'arrondi propre le plus proche des valeurs extrêmes (jamais les extrêmes bruts, jamais un zéro forcé), le pas est constant et choisi pour viser ~6 graduations, et le nombre de décimales des étiquettes se déduit du pas — deux graduations ne peuvent plus afficher le même nombre. Recalculé à chaque changement de période.
- **Échelle personnalisable** — un tracker `scale` définit son propre min/max/incrément (`TrackerModal`), plutôt qu'un simple « 1 à N » ; le curseur (Log, Historique, `EntryModal`) et l'axe du graphe (`ChartCard`) suivent.
- **Sens de l'amélioration** — un tracker `number`/`scale`/`duration` déclare si monter, descendre, ou se rapprocher d'une valeur cible est le progrès (`goodDirection`/`targetValue`, `TrackerModal`). `normalizeSeries` en tient compte pour tout composite (Master, Tendance générale) et `GridSummary` colore sa flèche de tendance en conséquence — un temps d'écran qui baisse se lit comme une amélioration, pas une chute.
- **Forme de courbe et granularité par tracker** — polyligne, courbe lissée ou bâtons, et un point = un jour / une semaine / un mois, réglables indépendamment dans la section « Vues » des paramètres du tracker (masters compris). Les bâtons partent de zéro quand l'échelle le contient, du bas du cadre sinon, et ne pontent pas les jours vides — un trait entre deux points affirme un passage que les bâtons ne prétendent pas connaître.
- **Tooltip flottant sur les graphes** — survol souris (immédiat) ou appui maintenu au doigt affiche la valeur du jour pointé, avec un bouton rond pour ouvrir ce jour dans l'Historique (édition directe) et un bouton rond pour fermer. Une fois ouvert, le doigt balaie librement la courbe.
- **Densité des cartes de graphe** — un curseur « − / + » règle de 1 à 4 cartes par ligne. Monter d'un cran ne fait pas que rétrécir : la carte se déleste de ses statistiques secondaires puis de ses graduations, et finit en sparkline avec sa seule valeur du jour. Bridé à 2 colonnes sous 880 px et à 1 sur téléphone.
- **Vue Master overlay** et **Tendance générale** — comparer plusieurs trackers normalisés sur le même graphe, ou leur moyenne lissée sur 7 jours.
- **Heatmap calendrier** par tracker (`CalendarCard`) et **grille de KPI** (`GridSummary`, avec variation vs période précédente).
- **Historique éditable** — calendrier mensuel, ouvrir/éditer n'importe quel jour passé.
- **Chronos** — plusieurs chronomètres, mode Solo/Multi, fenêtre flottante (Document Picture-in-Picture), conversion directe en entrée sur un tracker durée. Synchronisés sur le compte (voir « Architecture technique ») et réordonnables comme les cartes du Log.
- **Réordonnancement par glisser-déposer** — trackers, cartes du jour, master strips, chronos, **sections du Jour** ; un ordre global unique par liste (par mode de groupement pour les sections), chaque vue n'affiche/réordonne qu'un sous-ensemble sans perturber le reste (`mergeSubOrder`, `mergeSectionOrder`). Au doigt il faut maintenir l'appui avant que ça s'attrape, avec une brève vibration pour le dire.
- **Filtre, tri et groupe** (rail) — trois boutons désormais séparés : filtrer un sous-ensemble de trackers sur Log/Vues, trier Manuel/A→Z/Récents/Type, et **grouper** le "Jour" en sections par type (le cas d'origine), par couleur, ou par fait/pas fait aujourd'hui. Chaque section (Masters, Quotidiens, Plusieurs par jour, Alimentation, ou une section couleur/fait) se réordonne à la souris ou au doigt, comme une carte. Tout est retrouvé tel quel au rechargement ; un tracker supprimé ailleurs est purgé de la sélection une fois les trackers chargés.
- **Explications** — un seul interrupteur (Paramètres › Affichage) pour les descriptions écrites sous chaque réglage (`Help`) **et** les bulles « i » flottantes (`InfoBubble`). La règle de partage : inline là où il y a la place de l'écrire (page de réglages), bulle là où ça étoufferait le réglage (modale dense, carte, barre d'outils). Celle qui explique l'interrupteur lui-même ne se masque jamais — c'est la porte pour rallumer les autres.
- **Styles** — sélecteur à N styles (Sombre et Clair aujourd'hui), chaque choix montrant les couleurs qu'il applique. Préférence par appareil, appliquée avant le premier rendu pour ne jamais faire clignoter les mauvaises couleurs.
- **Onglets activables** — masquer Food, Vues, Training ou AI analyst depuis les paramètres. Rien n'est supprimé : l'onglet disparaît de la barre, les données restent. Log et les paramètres ne se masquent pas — l'un est la raison d'être de l'app, l'autre la seule porte pour rallumer le reste. L'analyse IA de Food **n'en fait pas partie** : ce n'est pas un onglet du haut mais une des quatre façons d'ajouter à manger, et on ne masque pas l'une sans les autres. Réglage synchronisé sur le compte.
- **Onglets réordonnables** — maintenir un onglet de la barre du haut (ou une ligne de Paramètres › Onglets) permet de le déplacer ; l'ordre suit le compte. Un onglet masqué garde son créneau et le retrouve quand on le rallume.
- **Nuancier de couleurs** — toutes les teintes (12, dont les 5 d'origine à leur valeur exacte), quatre paliers de luminosité, chroma constante, plus une ligne de neutres. Une couleur venue d'ailleurs reste sélectionnée et cliquable en fin de grille.
- **Numéro de semaine** — affiché à côté de la date du Log et de l'Historique, activable/désactivable dans les paramètres (Affichage). Préférence par appareil.
- **Retours intégrés** — bug, idée, avis ou autre, écrits depuis les paramètres et enregistrés en base, avec le contexte technique (style, taille d'écran, navigateur) capté automatiquement.
- **Items catégorisés** — quatre origines posées explicitement (aliment simple · aliment à code · item IA · personnel), une pastille sur chaque item partout où il se montre, et la sous-catégorie qui existait déjà (groupe Ciqual, marque) affichée à côté. L'origine était déjà dans le code ; elle est maintenant dite.
- **Une page d'ajout, quatre onglets** — Recherche · Mes items · IA · Ajout rapide. Le bouton principal de Food est « Ajouter », plus « Scanner un produit » : le scan est une façon d'ajouter, pas la porte d'entrée.
- **Food : scanner de code-barres** — caméra (BarcodeDetector natif ou ZXing en repli), plusieurs passes de recadrage/rotation. Il ne fait plus que scanner : ni photo de secours ni champ à lui. Un code qui ne se lit pas se tape dans le champ à côté (barre de recherche, ou champ code-barres de l'ajout rapide), qui reconnaissent une suite de chiffres pour ce qu'elle est.
- **Recherche Open Food Facts** — plusieurs moteurs en cascade, cache et limiteur de débit (quota OFF).
- **Table Ciqual embarquée** — recherche instantanée hors-ligne des aliments sans étiquette (légumes, viandes brutes…), avec micronutriments.
- **Snapshot nutritionnel** — chaque ligne de repas figée à sa valeur du moment ; corriger un aliment plus tard ne modifie pas l'historique.
- **Interrupteur caméra** — le scanner ne demande aucun flux tant qu'il est éteint ; le choix suit le compte, si bien qu'une fois allumé il démarre seul, ici comme sur l'autre appareil. Ce qui est synchronisé est l'intention « je veux la caméra » ; l'autorisation du navigateur, elle, reste propre à chaque appareil.
- **Favoris** — une étoile range un item dans les favoris, aliment comme repas, pour retrouver en un geste ce qu'on mange tous les jours.
- **Ligne d'item** — chaque résultat est une carte, avec la même rangée d'actions partout : à gauche ce qui touche à l'item (la corbeille pour **oublier** un aliment, le crayon pour ouvrir un repas) puis l'étoile ; à droite, seule, la flèche vers la fiche d'origine. Toutes sont des ronds `.icon-btn`.
- **Oublier un item** — la corbeille d'une ligne le retire de ce qui est à soi, après confirmation, comme s'il n'avait jamais servi. Les journées déjà notées ne bougent pas : chaque ligne de journal garde son instantané de valeurs, seul le lien vers la fiche disparaît.
- **Carte d'aliment** — une seule ligne d'actions : favori · modifier · supprimer, puis la source réduite à un bouton rond portant sa flèche (elle sort de l'app, elle ne pèse pas autant que ce qu'on fait dedans). La suppression est là, pas seulement au fond de la fiche d'édition.
- **Compteurs de Food** — les calories prennent toute la largeur, les trois macros se partagent la ligne suivante, et chaque objectif se lit « actuel / cible ». L'engrenage n'est que sur la carte calories : il ouvre les objectifs des quatre.
- **Repas enregistrés (presets)** — un ensemble d'ingrédients ajouté d'un coup, une ligne de journal par ingrédient (chacune reste corrigeable seule), avec une recette facultative en liste d'étapes. L'éditeur est une page à trois cadres — titre, ingrédients, recette — et chaque liste s'allonge par une ligne pointillée pleine largeur.
- **Composer un repas depuis n'importe quelle source** — « ＋ Ajouter un ingrédient » rouvre la page d'ajout en mode « choisir » : recherche, mes items, IA, à la main. Un repas peut donc contenir un produit scanné, un aliment Ciqual, une analyse IA, ou tous les ingrédients d'un autre repas versés d'un coup.
- **Étapes de recette** — le texte s'enroule sur plusieurs lignes, le rond numéroté se coche comme une todo (le texte passe en gris) et s'attrape en appui maintenu pour réordonner ; les numéros se refont tout seuls. Cocher n'est gardé que si on enregistre le repas — cocher en cuisinant puis fermer ne laisse aucune trace.
- **Minuteur d'étape** — une pastille facultative à côté de chaque étape (« 10 min »). Avec une durée, le rond numéroté change de métier : le premier tap lance le décompte (la pastille l'affiche, le rond bat), le second l'arrête en validant l'étape. Sans durée, il coche comme avant. La durée suit le repas ; le décompte, lui, ne vit que pendant qu'on cuisine.
- **Un aliment ne se corrige pas** — ni dans la bibliothèque, ni dans un repas. Ce qui vient de Ciqual ou d'Open Food Facts est traité comme la fiche de l'aliment, pas comme un brouillon : dans une recette, seul le **poids** d'un ingrédient se règle. Pour autre chose, l'onglet Créer fabrique l'aliment qu'on veut vraiment, et la corbeille oublie celui dont on ne veut plus.
- **Analyse IA d'un repas** — décrire un plat en texte, joindre une photo, ou les deux : envoyés dans la même requête, Claude le décompose en ingrédients pesés avec leurs valeurs pour 100 g, sa marge d'erreur et sa cause. La photo, quand elle est là, prime sur le texte pour la composition visible ; le texte sert à préciser ce qu'elle ne montre pas. Le résultat est entièrement éditable avant d'être versé au journal.
- **Normal / Approfondi** — une bascule au-dessus du bouton Analyser. En approfondi, le modèle cherche sur le web de vraies références (nommer l'établissement est ce qui lui donne quelque chose à chercher) et remplit les micronutriments, qui se cumulent alors dans le détail du jour comme ceux d'une étiquette. Ce qu'il a lu est affiché en clair sous le résultat.
- **En faire un item ?** — verser une analyse dans la journée et la garder dans Mes items sont deux gestes : la page pose la question (`Oui`/`Non`, oui par défaut). Une assiette de resto qu'on ne remangera jamais n'a pas à encombrer la bibliothèque ; un plat qu'on refait toutes les semaines, si.
- **Ajout rapide en trois modes** — un bloc de kcal/macros qui n'est pas un item (juste de quoi équilibrer la journée), un ingrédient qui en fabrique un, et le même avec son code-barres. Les trois partagent la même première section, au même endroit : changer de mode ajoute ou retire une section en dessous, ça ne redispose rien.
- **Objectifs nutritionnels** journaliers avec barres de progression et alerte dépassement, **datés** : régler un objectif le pose à partir du jour qu'on regardait, les jours précédents gardent le leur. Dans les Vues, la ligne d'objectif est une marche qui suit celui de chaque jour, et « dans la cible » compare chaque jour au sien.
- **Portions d'un repas** — une recette déclare en combien de parts elle se coupe ; l'éditeur affiche ce qu'une portion vaut, et l'ajout à une journée demande combien on en a prises (une demie comprise). Le facteur pèse chaque ingrédient, donc le journal garde une ligne par ingrédient, chacune juste.
- **Repas du jour en cartes** — les quatre moments de la journée sont quatre sections rectangulaires, comme le reste de l'app, plutôt que quatre titres qui coulent les uns dans les autres.
- **Sources en bulles** — le crédit reste écrit en une ligne (la licence d'Open Food Facts le demande) ; les paragraphes qui l'expliquent et la liste des liens passent derrière deux bulles « i ». Elles sont posées `always` : elles portent l'attribution, pas une explication de réglage, et ne suivent donc pas l'interrupteur des explications.
- **Retour immédiat après un enregistrement** — la page se referme sans attendre la base (voir « Écriture optimiste »), et un repas verse ses lignes en une seule insertion au lieu d'une par ingrédient.
- **Objectifs : la troisième macro se propose** — deux macros posées et une cible calorique ne laissent qu'une inconnue : le troisième champ l'affiche en placeholder, dans l'unité de SON mode (g, %, g/kg). Rien n'est enregistré tant qu'on n'a pas tapé — c'est une suggestion, pas une valeur.
- **Détail réglementaire + micronutriments** avec % des repères journaliers (AJR) quand disponibles.
- **PWA installable**, thème système, auth email/mot de passe + lien magique + réinitialisation.

## Architecture technique

- **Aucun build.** JSX transformé en direct dans le navigateur par `@babel/standalone`. Toute modif de `.jsx` est visible après rechargement — pas d'étape de compilation à lancer.
- **Persistance : Supabase** (Postgres + auth). Tables : `trackers`, `entries`, `foods`, `food_logs`, `nutrition_goals` (clé `(user_id, from_day)` : une ligne par prise d'effet, pas une par compte), `meals` (avec `source`, `favorite` et `portions` : un repas est un item comme un aliment), `user_settings`, `feedback`. Clé anonyme publique dans `app.jsx` (protégée par Row Level Security côté Supabase, pas un secret à cacher).
- **Ajouter un réglage de tracker = une migration SQL.** `trackerToRow` envoie des colonnes nommées : toute nouvelle propriété persistée demande un `alter table trackers add column …` **avant** de déployer, sinon tout enregistrement de tracker échoue — y compris la simple modification d'un tracker existant. Les colonnes doivent accepter `null` pour que les trackers existants continuent de fonctionner (le mapper applique la valeur par défaut à la lecture).
- **Les migrations peuvent être appliquées directement.** Le connecteur Supabase (MCP) donne accès au projet `drrmqrhsfgermgblndzz` : `apply_migration` pour le DDL, `execute_sql` pour l'inspection, `deploy_edge_function` pour les fonctions. Pas besoin de passer par l'éditeur SQL du dashboard — le faire directement évite l'écart entre « le code est poussé » et « la base suit », qui a déjà cassé l'enregistrement des trackers une fois. Les **secrets** restent l'exception : aucun outil ne les pose, `ANTHROPIC_API_KEY` se règle à la main.
- **Réglages : le compte fait autorité, `localStorage` n'est qu'un miroir.** `useSyncedPref(accountPrefs, clé, cléLocale, défaut)` lit le miroir pour le premier rendu, puis laisse le compte gagner et redescendre dans le miroir. Y passent : style, explications, numéro de semaine, interrupteur caméra. Reste vraiment local ce qui est un **état de travail** sur cet appareil, pas un réglage : le mode Solo/Multi des chronos, l'état ouvert/fermé et le mode du rail. Les chronos eux-mêmes ne sont **plus** de cette liste depuis leur passage à une table `chronos` + canal Realtime (`postgres_changes`) : démarré sur un appareil, un chrono doit se voir démarré sur l'autre — seul l'horodatage de départ traverse le réseau, le décompte affiché reste un calcul local (`chronoElapsed`, un `setInterval` par appareil). `AccountPrefsContext` porte `{ prefs, savePrefs }` jusqu'aux composants trop loin dans l'arbre pour qu'on leur passe le réglage à la main — au premier chef le scanner de la page Food.
- **`app.food.jsx` dépend du scope global posé par `app.jsx`** (React, `supabase`, `dayKey`, `uid`, `startOfDay`…) — les deux fichiers sont deux `<script>` distincts mais partagent un seul espace de noms global, chargés dans cet ordre puis montés ensemble (`mountTracklog()`).
- **Drag & drop maison** (`useDragReorder`) — pointer events, pas de librairie ; un ordre global par tracker, chaque vue réordonne un sous-ensemble reconstitué dans l'ordre complet.
- **Cache-busting manuel** — les `<script src="app.jsx?v=N">` portent un numéro de version à incrémenter à la main dans `Tracklog.html` pour forcer le rechargement (pas de hash de build automatique).
- **Aucun framework CSS** — tout le style est dans `<style>` en tête de `Tracklog.html`, thème "Aristide" (variables CSS `--bg`, `--ink`, `--accent`…, clair/sombre via `data-theme`).
- **`Segmented` (app.jsx) est le seul mécanisme de bascule de l'app.** Jour/Historique/Chrono, Oui/Non, le type d'un tracker, Graphes/Calendrier/Grille — tout passe par ce composant plutôt que par du CSS qui swappe un fond en place. Un fond (`.seg-thumb`) *glisse* jusqu'à l'option portant `.on`, mesuré en JS via `offsetLeft`/`offsetTop`/`offsetWidth`/`offsetHeight` du bouton actif (pas `getBoundingClientRect()` : la différence de deux rects inclut la bordure de la piste et décale le thumb d'un pixel). Migrer un ancien `<div className="vue-mode">…</div>` est volontairement un remplacement de balise à l'identique : `Segmented` ne réclame aucun changement aux `<button>` qu'il enveloppe, il regarde juste lequel porte `.on` après chaque rendu. Trois tailles nommées, pas des variantes accidentelles : par défaut (chips à leur propre contour, texte en minuscule — les options d'une modale), `size="compact"` (piste unique en capitales tassées — la nav principale), `size="small"` (la même piste compacte, un cran plus petit — tri du rail, onglets, densité des graphes). `BoolPill` est un `Segmented` à deux options (`size="compact"`) ; ne pas réintroduire de `<input type="checkbox">` pour un réglage binaire.
- **Convention visuelle des cartes** — nom en gras teinté de la couleur du tracker en haut à gauche (jamais de puce `.dot` à côté), engrenage rond (`.chart-edit-btn`) vers `TrackerModal` en haut à droite : partagée par `DayCard`, `ChartCard`, `CalendarCard` et les tuiles de `GridSummary`. `MasterTrackerCard`/`MasterStrip` gardent leur propre marqueur (`.master-mark`, un losange) plutôt que la puce ronde d'un tracker de données — c'est un langage visuel volontairement distinct pour un composite.
- **`IconBar` (app.jsx) est l'autre forme de contrôle partagée.** Une barre pleine largeur, un bouton rond, et deux formes qui veulent dire deux choses : `inset` (le bouton est dans la barre — il la remplit autrement) et `detached` (le bouton est à côté — il agit sur ce que la barre montre). Poser un `<input>` et un `.icon-btn` côte à côte à la main referait la même chose en moins bien : passer par `IconBar` est ce qui garde la recherche de Food, sa bascule Mes items et le champ code-barres identiques. En forme `detached`, une saisie nue reçoit le contour de la barre (`.icon-bar.detached>.icon-bar-field>input`) ; un contenu qui a déjà le sien — un `Segmented` — n'en reçoit pas. Le code-barres de l'ajout à la main est en forme `inset` (le champ *est* la barre) : le bouton n'y ajoute qu'une seconde façon d'écrire le même champ, comme la recherche et son scanner — la forme suit le sens, pas l'écran où le composant se trouve.
- **Une liste d'items ne défile pas dans son propre cadre.** `.fd-list` remplissait 46vh et défilait à l'intérieur d'une page qui défile déjà : deux ascenseurs imbriqués, et un tiers d'écran utilisé pour montrer ce qu'on est venu chercher. C'est la page qui défile ; la liste s'étend.
- **`Segmented` a deux réponses à « trop d'options pour une ligne », pas une.** `wrap` repasse à la ligne (le rail, un réglage à cocher). `scrollx` garde une seule ligne et la fait glisser au doigt — pour un choix court et exclusif qui doit rester entièrement à un tap (repas, mode d'ajout, tabs de la page d'ajout) : une deuxième ligne avec un seul bouton dessus a l'air cassée, un menu déroulant cacherait des options qui doivent rester visibles. `scrollx` recentre aussi l'option choisie dans la fenêtre visible après coup (measure() dans `Segmented`), pour qu'un choix par défaut en bout de piste (« Dîner ») ne se retrouve pas hors champ.
- **`NumField` (app.food.jsx) est la seule rangée de champ numérique.** Label à gauche, saisie + unité à droite — la même forme que tout `.field` de l'app (`.field-num` en est le corps). Trois formulaires (repas perso, ajout à la main, éditeur d'ingrédient IA) posaient chacun leur variante avant de converger ici ; une future page qui demande des macros doit repasser par `NumField`, pas en inventer une quatrième.
- **`.icon-btn` est le seul rond à icône ou glyphe seul.** Engrenage d'une carte, flèche du calendrier, croix de suppression, lien source — la forme (cercle, contour, transition) et la taille sont partagées par cette classe, ajoutée à côté du nom sémantique de chaque bouton (`className="icon-btn chart-edit-btn"`, `className="icon-btn cal-nav"`…) qui garde lui la couleur et le survol propres à son usage — un survol qui vire au rouge pour une suppression n'a pas à ressembler à un survol neutre. Deux tailles seulement : par défaut (26px) et `.sm` (20px, pour une tuile de la Grille, une infobulle flottante, une bulle d'aide). `.gear-btn` (l'engrenage de la barre du haut, qui pivote au survol) et `.tc-act` (la rangée d'actions d'une carte du Log, où l'icône engrenage doit rester à la même hauteur que les boutons texte à côté) restent volontairement hors de cette famille — ce sont des interactions à part, pas des rappels d'un même bouton.
- **Les boutons d'accent plein (`.btn-primary` et alliés) partagent une seule taille.** `.save button.primary`, `.modal-actions .primary`, `.submit-all`, `.chrono-add-big`, `.fd-primary` sont groupés sur une même déclaration de padding/police ; seuls leur survol et leurs états (`:active`, `:disabled`) restent propres à chacun. `.tc-act.primary` (Noter/Ajouter dans une carte du Log) reste à part, délibérément plus compact — il doit rester à la hauteur du reste de sa carte, pas de celle d'un CTA pleine largeur.

## Décisions et pièges connus

- **Joker ≠ zéro.** Un jour joker est *exclu* des agrégats, jamais compté comme 0 — vérifier `isJokerEntry`/`jokerDayKeys` avant toute nouvelle fonction de calcul.
- **Master ne forward-fill jamais.** `computeMasterSeries` laisse les trous en trous (dessinés en pointillés) plutôt que de reporter la dernière valeur connue — un master ne doit jamais paraître à jour alors que ses membres ne le sont plus.
- **Une entrée "quotidienne" remplace, ne s'additionne pas** (`addEntry` dans `App`, logique `tracker.daily`).
- **`app.food.jsx` n'a pas de `const { useState... } = React` à lui** — il compte sur celui déclaré en tête de `app.jsx`. Ne jamais réordonner le chargement des deux scripts dans `Tracklog.html`.
- **Ajouter un style se fait à trois endroits, pas un.** Le bloc de tokens CSS, l'entrée dans `STYLES` (app.jsx), et l'id dans `STYLE_IDS` du script en tête de `Tracklog.html`. Ce dernier tourne avant tout chargement de script, il ne peut donc pas lire `STYLES` — la duplication est délibérée, et c'est elle qui évite le flash de mauvaises couleurs au chargement.
- **Une explication a deux formes, et une seule règle pour choisir.** `Help` écrit la description sous le réglage (page de paramètres : la description fait partie de ce qu'on vient lire) ; `InfoBubble` la range derrière un « i » (modale dense, carte, barre d'outils : l'écrire étoufferait ce qu'elle explique). Les deux obéissent au même interrupteur, via `InfoVisibilityContext`. Seule exception, volontaire : la description de l'interrupteur lui-même reste toujours écrite — c'est elle qui dit comment rallumer les autres.
- **Une table manquante ne doit jamais bloquer l'app.** `user_settings` et `meals` sont lues en tolérant l'erreur : migration pas encore passée = valeurs par défaut, pas d'écran blanc. Garder ce réflexe pour toute nouvelle table.
- **La clé API Anthropic ne doit jamais atteindre le navigateur.** Elle vit en secret d'Edge Function (`supabase secrets set ANTHROPIC_API_KEY=…`). L'analogie avec la clé anon Supabase est trompeuse : celle-ci est inoffensive parce que Row Level Security la borne, la clé Anthropic n'a aucune protection équivalente et se dépense.
- **Un ingrédient porte ses valeurs pour 100 g, jamais ses valeurs absolues.** C'est ce qui permet de changer un poids sans rappeler le modèle ni la base. `itemNutriments()` fait la mise à l'échelle au moment de l'affichage et de l'écriture du journal.
- **Un repas ajouté produit une ligne de journal par ingrédient**, pas une ligne agrégée — chacune reste corrigeable et supprimable seule, et garde son snapshot comme n'importe quel ajout.
- **OFF (Open Food Facts) a un quota de recherche serré** (~10 req/min) — `takeSearchToken`/cache dans `app.food.jsx` ; ne pas retirer le limiteur sans comprendre pourquoi il existe (429 sinon).
- **Le SVG des graphes est étiré (`preserveAspectRatio="none"`), donc son texte l'est aussi.** Une carte deux fois plus étroite comprime ses graduations d'autant : à 250 px elles deviennent des taches. C'est pourquoi `chartDetail()` coupe les étiquettes d'axe (`axisLabels:false`) au cran serré au lieu de simplement réduire la police — rapetisser le texte ne le rendrait pas lisible. Toute nouvelle légende posée dans ces `<svg>` subit la même déformation.
- **Un geste tactile qui s'arme doit d'abord laisser défiler.** Le glisser et la lecture d'un graphe attendent un appui immobile avant de prendre la main, et surtout n'appellent ni `preventDefault` ni écouteur bloquant pendant l'attente : le navigateur doit rester libre de faire défiler si le doigt part. `touch-action` est passé de `none` à `pan-y` sur les poignées et les pastilles pour la même raison. Une fois armé, un écouteur `touchmove` non passif annule le défilement — posé alors que le doigt est encore immobile, seul moment où `preventDefault` peut encore l'empêcher de démarrer.
- **Un appui long ne doit pas valider le clic au relâchement — un simple clic, si.** Une pastille du rail bascule le filtre au clic ; sans garde-fou, la maintenir pour la réordonner basculait aussi le filtre en la relâchant. `useDragReorder` expose `wasArmed()` pour ça. Mais « armé » ne veut pas dire « pointeur posé » : à la souris le glisser démarre dès le `pointerdown`, et considérer le clic comme consommé à ce moment-là rendait muettes toutes les pastilles du rail — cliquer pour filtrer ne faisait plus rien sur PC. `armedRef` ne passe donc à vrai que quand le geste a vraiment pris la main : un appui long au doigt (qui a tenu), ou un pointeur qui bouge. Le garde-fou de distance qui l'accompagne (6 px) suppose des coordonnées de clic réelles — un `click()` programmatique en (0,0) se fait légitimement avaler, ce qui trompe un test avant de tromper un utilisateur.
- **Une réponse PostgREST, c'est `{ data, error }` — les colonnes sont sur `data`.** Les objectifs nutritionnels lisaient `g.kcal` au lieu de `g.data.kcal` : quatre `null`, donc des objectifs qui revenaient vides à chaque ouverture alors qu'ils étaient bien enregistrés en base — et un objet quand même présent, donc `goalsSet` répondait « oui, c'est réglé ». Un bug d'affichage qui se lit comme une perte de données.
- **Le blob de préférences s'écrit en entier : ne jamais l'écrire avant de l'avoir lu.** `savePrefs` remplace tout `prefs` ; un réglage touché avant la réponse de la base aurait écrasé les onglets du compte avec un objet à une seule clé. Les patches d'avant-chargement sont donc mis de côté (`pendingRef`) et rejoués par-dessus ce qui arrive.
- **Une hauteur héritée d'un `stretch` ne nourrit pas un `aspect-ratio`.** Le « + » du Log prend sa hauteur sur la ligne (`align-self:stretch`, aucun nombre à tenir à jour) ; pour en faire un rond, `aspect-ratio:1` ne suffisait pas — la largeur restait celle du glyphe. La largeur vient donc du même jeton `--ctl-h` que la hauteur minimale de la barre d'onglets compacte : un seul nombre, deux règles qui ne peuvent pas diverger.
- **Renommer un onglet ne renomme pas ce qui est déjà enregistré.** L'onglet « Bouffe » est devenu « Food » (id `bouffe` → `food`), mais les comptes existants portent encore l'ancienne clé dans `prefs.tabs` : sans relecture, un onglet masqué serait réapparu au prochain chargement. `useAccountPrefs` reporte donc l'ancienne valeur sur la nouvelle clé tant que celle-ci n'existe pas. Même réflexe pour tout futur renommage d'id persisté.
- **Un nom long doit se couper, jamais élargir sa carte.** Une case de grille vaut par défaut `min-width:auto` — « au moins la largeur de mon contenu » — donc une carte au nom à rallonge imposait 692 px à une colonne de 354 px. Et `html{overflow-x:hidden}` masquait le débordement au lieu de le signaler : la carte était simplement coupée, hors d'atteinte. D'où la règle `.today-grid>*,.trackers-grid>*,.gridview>*,.chart-grid-layout>*{min-width:0}` : sans elle, aucune troncature interne ne peut entrer en jeu. Corollaire pour tester : `overflow-x:hidden` rend un contrôle de défilement horizontal aveugle — comparer la largeur des cartes à celle de la fenêtre.
- **Un objectif se lit toujours POUR UN JOUR.** Il n'existe plus de « l'objectif » global : `effectiveGoalsAt(jour)`, `goalsSetAt(jour)`. Toute nouvelle vue qui compare un total à une cible doit demander celle du jour concerné — sinon elle jugera le mois dernier à l'aune de la consigne d'aujourd'hui, ce qui est exactement ce que la datation existe pour éviter. La comparaison de dates se fait sur les chaînes `AAAA-MM-JJ`, dont l'ordre lexicographique est l'ordre chronologique : rien à convertir.
- **Un ingrédient n'est pas un brouillon.** Nom et valeurs pour 100 g sont en lecture seule dans une recette : les retoucher ferait dire à « riz » deux choses différentes selon le repas, et ferait diverger silencieusement les copies d'une même fiche. Seul le poids se règle — ce n'est pas une propriété de l'aliment, c'est la quantité qu'on en met.
- **Les portions divisent, elles ne remplacent pas.** Les ingrédients d'un repas pèsent toujours la recette entière ; `portions` ne fait que dire en combien elle se coupe. Stocker l'inverse (des ingrédients par portion) obligerait à retoucher chaque ligne dès qu'on change le nombre de parts.
- **Le numéro d'une étape n'est pas une donnée.** Il se lit de la position dans la liste (`order.map((id, i) => i + 1)`), jamais d'un champ enregistré : le stocker obligerait à renuméroter toute la liste à chaque glisser, et une seule renumérotation ratée laisserait deux « 3 » côte à côte.
- **Le rond d'une étape porte deux gestes, comme une pastille du rail.** Un tap coche, un appui maintenu attrape pour réordonner — donc le même garde-fou `wasArmed()` qu'ailleurs, sans quoi relâcher après un glisser cocherait par-dessus le marché. Et `touch-action:pan-y` dessus : tant que l'appui n'a pas tenu, le doigt doit encore pouvoir faire défiler la page.
- **Un ajout rapide n'est pas un item, et c'est délibéré.** Poser 450 kcal parce qu'on connaît l'étiquette d'un sandwich qu'on ne remangera jamais ne doit pas créer une fiche de plus dans la bibliothèque. Les deux autres modes de l'ajout rapide, eux, en créent une — la différence est portée par un seul drapeau (`keep`) et par le mode qui le décide, pas par une case à cocher que l'utilisateur oublierait.
- **`useDragReorder` réconcilie son ordre par identité de clé d'un rendu à l'autre — deux listes qui partagent une clé littérale se marchent dessus.** Les sections du Jour groupées par « type » et par « fait/pas fait » utilisent toutes deux l'id `masters` : changer de groupement ne démonte pas le hook (le composant reste monté), donc son effet de reconciliation voyait `masters` déjà présent dans son ordre interne précédent et lui gardait sa position, mélangeant l'ordre par défaut d'un mode avec les clés du mode précédent. Fixé en préfixant chaque clé de section par le mode (`type:masters`, `done:masters`…) — jamais de clé partagée entre deux listes réordonnables indépendantes, même quand leur contenu se recoupe.
- **`wrap` doit battre le `nowrap` de la piste compacte.** `.seg-track.wrap` et `.seg-track.small` ont la même spécificité : la dernière règle écrite gagnait, donc `<Segmented size="small" wrap>` ne repliait rien et une piste de quatre options débordait de son propre contour sur téléphone. D'où la règle à trois classes `.seg-track.compact.wrap,.seg-track.small.wrap`.
- **`button.primary.sm` n'avait aucune règle.** Le bouton d'accent qui vit *dans* un panneau (Analyser, dans l'onglet IA) se rendait en texte nu : les styles d'accent sont accrochés à `.modal-actions .primary` et `.save button.primary`, pas à `.primary` seul. Toute nouvelle place pour un bouton d'accent doit être ajoutée à cette famille, pas décorée sur place.
- **Une écriture optimiste doit savoir se défaire.** Poser l'état local avant la réponse de la base fait gagner l'aller-retour, mais supprime le `return` qui arrêtait tout en cas d'échec : chaque écriture de `useFoodStore` garde donc de quoi revenir en arrière (la ligne insérée, l'objet d'avant) et appelle `writeFailed`. Un échec muet est ce qui a déjà fait croire à des objectifs enregistrés qui ne l'étaient pas.
- **Le JSON d'une réponse à outils est dans le DERNIER bloc texte, pas dans tous.** Avec la recherche web, la réponse contient les tours intermédiaires du modèle ; les concaténer comme avant rend un texte illisible dès qu'une recherche a eu lieu. Et un tour long peut rendre `stop_reason:'pause_turn'` : il faut renvoyer le message de l'assistant **tel quel** (les résultats de recherche y sont chiffrés) pour qu'il reprenne.
- **Une bulle ancrée à son bouton sort de l'écran quand le bouton est à gauche.** `.info-pop` est calée `right:0` sur son `.info` : parfait pour une bulle en fin de ligne, hors champ pour la première d'une barre. Dans les sources, `.info` repasse donc `position:static` sous 700 px, ce qui fait de la barre l'ancre — et la bulle s'ouvre vers le haut, puisque les sources sont en pied de page.
- **Cache-busting manuel** — après une modif de `app.jsx` ou `app.food.jsx`, penser à incrémenter le `?v=` correspondant dans `Tracklog.html`, sinon des utilisateurs peuvent rester sur une version en cache.
- **Pas de tests automatisés, pas de build.** Toute validation passe par relecture + test manuel dans un navigateur (le fichier compile-t-il via Babel, l'app charge-t-elle sans erreur console).
- **Workflow de branche actuel** : développement direct sur `Tracklog_V1` (branche par défaut = celle publiée), pas de branche de feature intermédiaire — voir historique de commits pour le contexte.
